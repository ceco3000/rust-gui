### 2.1 文件监控

使用 `notify` crate 监控项目目录。监控策略：

- 递归监控 `src/`、`styles/`、`assets/`
- Debounce：合并 300ms 内的多次保存为一次重载
- 按文件扩展名路由到对应的热重载处理器

```rust
pub struct DevTools {
    watcher: notify::RecommendedWatcher,
    style_reloader: StyleHotReload,
    debounce_timer: Option<Instant>,
}

impl DevTools {
    pub fn new(project_dir: &Path) -> Result<Self, notify::Error> {
        let mut watcher = notify::recommended_watcher(|event| {
            // 事件处理见子模块
        })?;
        watcher.watch(project_dir, notify::RecursiveMode::Recursive)?;
        Ok(DevTools { watcher, style_reloader: StyleHotReload::new(project_dir.join("styles")).map_err(|e| notify::Error::new(notify::ErrorKind::Generic(e.to_string())))?, debounce_timer: None })
    }
}
```

### 4.2 App 集成 API（阶段 2 实现）

`rgui` facade crate 通过 `AppConfig` 和 `App` 方法暴露 `.rgui` 加载能力。

#### AppConfig 新增字段

```rust
pub struct AppConfig {
    // ... 现有字段 ...
    /// 可选 `.rgui` 文件路径，作为视图源（替代 `set_view_scene_builder`）。
    /// `App::load_rgui::<M>()` 从此字段读取路径。
    pub rgui_path: Option<PathBuf>,
}
```

#### App 新增方法

```rust
impl App {
    /// 从 `.rgui` 文件加载视图（路径从 `config.rgui_path` 读取，无需重复传入）。
    ///
    /// `M` 为 AppMessage 类型，用于解析器泛型参数。
    /// 内部创建 `RguiHotReload<M>`，每帧轮询文件变更，
    /// 变更时重新解析 → `compute_view_layout` → `build_scene_from_view` → `SceneGraph`。
    ///
    /// 必须在 `run()` 之前调用。返回 `Err` 如果 config 未设置 `rgui_path`。
    ///
    /// 解析失败时保持旧视图，通过 stderr 报告错误（D7 §9 降级策略）。
    pub fn load_rgui<M: AppMessage>(&mut self) -> Result<(), RguiHotReloadError>;
}
```

#### AppHandler 集成点

1. **启动前**（`App::run()` 内部，`AppHandler::new()` 之前）：
   - `view_scene_builder` 已由 `load_rgui::<M>()` 设置
   - `AppHandler` 直接使用该回调，无需额外初始化

2. **每帧渲染前**（`RedrawRequested`）：
   - 更新逻辑已封装在 `load_rgui` 创建的 `ViewSceneBuilder` 闭包中
   - 每帧自动 `RguiHotReload.check_and_reload()` → 若有新视图 → 自动更新 `SceneGraph`

3. **降级策略**（D7 §9）：
   - `.rgui` 解析失败 → 保持旧视图，stderr 输出错误
   - 文件不存在 → `load_rgui` 返回 `Err`

#### 依赖关系

```
rgui (facade) ──→ rgui-devtools (feature: devtools, 现有依赖)
```

> `.rgui` 解析和热重载全部在 `rgui-devtools` 中，不需要 `rgui-script`。

#### 用户使用示例

```rust
use rgui::app::{App, AppConfig};
use rgui::AppMessage;

#[derive(Debug, Clone, PartialEq, AppMessage)]
enum Msg { Clicked }

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = AppConfig::new()
        .title("rgui App")
        .rgui_path("ui/app.rgui");  // 新增

    let mut app = App::new(config);
    app.register_defaults();
    app.load_rgui::<Msg>()?;  // 新增，路径从 config.rgui_path 读取
    app.load_rhai_scripts(&["scripts/handlers.rhai"])?;  // 新增，见 §10.2
    app.run()
}
```

## 5. 第 3 层：Rust 逻辑反馈（快速重启）

### 5.1 完整流程

```
1. .rs 文件保存
2. cargo build 增量编译（sccache，目标 2-5s）
3. DisplayProcess 检测二进制更新
4. 捕获当前状态快照 + RestoreMetadata
5. DisplayProcess 启动新的 AppProcess
6. IPC 发送 IpcMessage::RestoreState { snapshot, metadata }
7. 新 AppProcess 恢复 StateStore
8. 所有 widget 重新 view()
9. 恢复焦点、滚动位置
10. DisplayProcess 渲染第一帧
11. 旧 AppProcess 退出
```

### 5.2 序列图

```
DisplayProcess              Cargo              AppProcess(new)
     │                        │                      │
     │ .rs 变更                │                      │
     │──→ cargo build ───────→│                      │
     │                        │← 编译完成 ───────────│
     │←── 通知 ──────────────│                      │
     │                        │                      │
     │ 捕获快照 + 元数据       │                      │
     │──→ 启动新进程 ─────────┼─────────────────────→│
     │──→ IPC: RestoreState ─┼─────────────────────→│
     │                        │                      │ 恢复 StateStore
     │                        │                      │ view() 重建
     │←── IPC: Ready ────────┼──────────────────────│
     │ 替换渲染源              │                      │
     │──→ IPC: Shutdown ─────┼─────────────────────→│ (旧进程)
```

## 6. 双进程架构

### 6.1 进程职责

```
┌──────────────────────┐     IPC (Unix Domain Socket / Named Pipe)
│   DisplayProcess      │◄══════════════════════════════════►
│                       │                                    │
│  - 窗口管理 (winit)    │         ┌──────────────────────────┴──────────┐
│  - GPU 渲染 (wgpu)    │         │     AppProcess                       │
│  - 输入事件接收        │         │                                      │
│  - 文件监控 (notify)   │         │  - Widget 树维护                     │
│  - 热重载触发          │         │  - StateStore 管理                   │
│                       │         │  - 业务逻辑执行                      │
└──────────────────────┘         │  - view()/update()/paint() 调用      │
                                  └─────────────────────────────────────┘
```

### 6.2 设计理由

- **进程隔离**：AppProcess panic 不影响 DisplayProcess，窗口保持显示
- **GPU 上下文保持**：DisplayProcess 重启，AppProcess 独立重启
- **编译隔离**：AppProcess 二进制独立编译，DisplayProcess 不参与重编译

### 6.3 阶段 1 简化

阶段 1（MVP）中，DisplayProcess 和 AppProcess 合并为单进程。双进程架构在阶段 2 引入。阶段 1 的"快速重启"降级为普通重启（退出 → `cargo build` → 手动重新启动），状态通过文件系统保存和恢复。

## 7. IPC 协议设计

```rust
/// IPC 消息协议（serde 序列化，postcard 二进制格式）。
#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum IpcMessage {
    /// DisplayProcess → AppProcess：状态快照 + 元数据
    RestoreState { snapshot: Vec<u8>, metadata: RestoreMetadata },

    /// AppProcess → DisplayProcess：就绪信号
    Ready { widget_count: u32 },

    /// AppProcess → DisplayProcess：场景图更新（全量或增量）
    SceneUpdate { scene_data: Vec<u8>, incremental: bool },

    /// DisplayProcess → AppProcess：输入事件
    InputEvent { event_data: Vec<u8> },

    /// DisplayProcess → AppProcess：终止信号
    Shutdown,

    /// AppProcess → DisplayProcess：可恢复错误
    Error { message: String, recoverable: bool },
}

/// IPC 传输层。
pub struct IpcChannel {
    stream: UnixStream,  // Unix: UnixStream; Windows: NamedPipe
    read_buffer: Vec<u8>,
}

impl IpcChannel {
    pub fn send(&mut self, msg: &IpcMessage) -> Result<(), IpcError> {
        let data = postcard::to_vec(msg)?;
        // 写入长度前缀 + 数据
        let len = data.len() as u32;
        self.stream.write_all(&len.to_le_bytes())?;
        self.stream.write_all(&data)?;
        Ok(())
    }

    pub fn recv(&mut self) -> Result<IpcMessage, IpcError> {
        let mut len_buf = [0u8; 4];
        self.stream.read_exact(&mut len_buf)?;
        let len = u32::from_le_bytes(len_buf) as usize;
        self.read_buffer.resize(len, 0);
        self.stream.read_exact(&mut self.read_buffer)?;
        Ok(postcard::from_bytes(&self.read_buffer)?)
    }
}
```

## 8. 状态恢复与序列化

### 8.1 传输格式

```rust
/// RestoreMetadata：快照前的交互上下文（D2 §8.2 已有定义，此处引用）。
/// 使用 HashMap 以兼容 serde（FxHashMap 不实现 Serialize/Deserialize）。
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct RestoreMetadata {
    pub focus_path: Vec<u64>,
    pub scroll_positions: HashMap<u64, (f64, f64)>,
    pub current_route: String,
    pub window_geometry: (i32, i32, u32, u32),
}
```

### 8.2 恢复流程

```
AppProcess 接收 IpcMessage::RestoreState { snapshot, metadata }
  → Snapshotter::restore(snapshot, &mut state_store, &migrations)  // 需在 D2 Snapshotter 中补充 restore() 方法
  → 遍历 snapshot.states → 按 WidgetId 反序列化 → 插入 StateStore
  → 应用 metadata:
      focus_path → FocusManager::focus()
```

## 9. 降级策略

```
级别              失败原因                 降级行为
─────────────────────────────────────────────────────
样式热重载         .rgss 语法错误           保持旧样式，显示错误信息
结构热重载         .rgui 解析失败           保持旧结构，显示错误信息
快速重启           增量编译失败             重试 cargo build（最多 3 次）
快速重启           AppProcess 启动超时(>10s) 降级为普通重启
快速重启           状态恢复失败              清空状态，从 App::new() 冷启动
普通重启           二进制崩溃                DisplayProcess 显示错误画面
                                              + "状态已保存到 xxx" 提示
IPC 通信           IPC 断连                  DisplayProcess 显示重连动画
                                              自动重连（最多 5 次）
```

#### 事件路由——`handle_click` 集成

点击事件路由优先级（从高到低）：

1. **WidgetSpec 实例处理器**（现有，`widget_instances`）——组件内部 update()
2. **Rhai 命令处理器**（新增）——`command_registry.call_fn(action, ())`

```rust
    match registry.call_fn::<()>(&action, ()) {

        Err(_) => { /* Rhai 无此函数，继续传播 */ }
    }
}
// 继续现有 fallback 路径
```

#### AppHandler 集成点

`AppHandler` 需新增两个字段（由 `App::run()` 内 `AppHandler::new()` 从 `App` 中 `.take()` 传入）：

```rust
struct AppHandler {
    // ... 现有字段 ...
    /// Rhai 命令处理器注册表（从 App 移入，仅当 load_rhai_scripts 被调用时存在）。
    #[cfg(feature = "devtools")]
    command_registry: Option<CommandRegistry>,
    /// Rhai 脚本热重载管理器（从 App 移入，每帧轮询）。
    #[cfg(feature = "devtools")]
    rhai_hot_reload: Option<RhaiHotReload>,
}
```

1. **启动时**（`AppHandler::new()`）：
   - 若 `App.command_registry` 非空，`.take()` 移入 `AppHandler`
   - 若 `App.rhai_hot_reload` 非空，`.take()` 移入 `AppHandler`
   - 无需在 `resumed()` 中初始化（已在 `App` 端完成）

2. **每帧渲染前**（`RedrawRequested`）：
   - `RhaiHotReload.check_and_reload()` → 若有变更自动重新编译

3. **事件分发**（`handle_click`）：
   - 在现有 WidgetSpec 处理器之后、旧回调之前插入 Rhai 路由

4. **降级策略**（D7 §9）：
   - `.rhai` 编译失败 → 保留旧 AST，stderr 输出错误
   - 函数调用 panic → `catch_unwind` 隔离，stderr 报告，不崩溃

```
rgui-devtools ──→ rgui-script (已添加)
```

### 10.3 Rhai 响应式状态桥接（P2 — 待开发）

> **设计依据：** D0 §6.2 完整事件处理链步骤 3a：
> "Rhai 脚本处理消息 → 调用 StoreAccessMut"。
> RH01-RH05 已完成事件路由（onclick → Rhai call_fn），
> 但 Rhai 修改状态后回写到 WidgetView 树的桥未搭。
> 本节定义桥接架构，对应实现任务 RS01-RS07。

> **⚠️ 任务编号以 D8 §9.16b 为权威来源，本文档引用须保持一致。**

#### 问题

当前 `.rgui` + `.rhai` 管线：

```
ui.rgui → parse → WidgetView（静态）
onclick → Rhai call_fn → print（无副作用）
```

Rhai 函数执行后无法修改 WidgetView props，导致 accordion/dialog/dropdown
等交互组件的展开/折叠/开关操作无法产生视觉变化。

#### 架构：三层桥接

```
┌──────────┐  set_prop()    ┌─────────────┐  Arc<RwLock>  ┌──────────────┐
│  .rhai   │ ────────────→  │ PropRegistry │ ────────────→ │ WidgetView   │
│ 脚本     │  get_prop()    │ (rs01-rs02)  │              │ Prop 变更    │
└──────────┘                └─────────────┘              └──────┬───────┘
                                                               │ rs04 drain
                                                               ▼
┌──────────┐  store_write()  ┌─────────────┐  Subscription  ┌──────────────┐
│  .rhai   │ ────────────→   │ StateStore   │ ──────────────→│ Widget        │
│ 脚本     │  store_read()   │ (rs05-rs06)  │               │ view/layout   │
└──────────┘                 └─────────────┘               │ /paint        │
                                                           └──────────────┘
```

#### 第 1 层：PropRegistry 直写（RS01-RS04，MVP）

Rhai 侧注册 `set_prop(id, key, value)` 和 `get_prop(id, key)` 函数。
`PropRegistry` 为 `Arc<RwLock<HashMap<WidgetId, BTreeMap<String, PropValue>>>>`，
在 `view_scene_builder` 闭包中每帧 drain 待写入 prop 到 WidgetView 树。

- **RS01 PropRegistry 类型定义** — 定义 `PropRegistry` 类型，提供 `set(id, key, value)` /
  `get(id, key)` / `drain()` 方法。锁设计：建议使用 `DashMap` 或 per-widget `RwLock`
  降低写锁竞争（渲染线程 drain 与 Rhai set_prop 并发）。
- **RS02 Rhai 侧 set_prop/get_prop 注册** — 在 `CommandRegistry` 中向 Rhai 引擎注册
  `set_prop(id: &str, key: &str, value: &str)` 和 `get_prop(id: &str, key: &str) -> String`
  函数，内部调用 RS01 的 PropRegistry。
- **RS03 WidgetId 字符串双向映射** — `.rgui` 中 `id="section1"` 解析为 WidgetId 查找表
  （正向 `String → WidgetId`），同时维护反向映射 `WidgetId → String`，
  供 `handle_click` 将点击的 widget_id 转回字符串 id 传给 Rhai。
- **RS04 view_scene_builder 消费 PropRegistry** — `load_rgui<M>` 内部闭包每帧调用
  `PropRegistry::drain()` 获取待写入 prop，注入到 WidgetView 树对应节点，
  触发 `compute_view_layout` + `build_scene_from_view`。

> **注意**：RS03 不依赖 RS02（字符串映射在解析阶段完成，不需 Rhai 引擎）。
> RS04 依赖 RS02（PropRegistry）+ RS03（字符串 id 定位 WidgetId）。

此层完成后，`one-accordion` 可写为：

```xml
<!-- ui.rgui — 每 section 独立 onclick，避免参数解析 -->
<WaAccordion>
  <WaAccordionItem id="s1" label="Section 1" expanded="true"
                   onclick="toggle_s1"/>
  <WaAccordionItem id="s2" label="Section 2" expanded="false"
                   onclick="toggle_s2"/>
</WaAccordion>
```

```rust
// handlers.rhai
fn toggle_s1() {
    let current = get_prop("s1", "expanded");
    if current == "true" {
        set_prop("s1", "expanded", "false");
    } else {
        set_prop("s1", "expanded", "true");
    }
}
fn toggle_s2() {
    let current = get_prop("s2", "expanded");
    if current == "true" {
        set_prop("s2", "expanded", "false");
    } else {
        set_prop("s2", "expanded", "true");
    }
}
```

> **为什么不用 `onclick="toggle('s1')"` 带参数？** 
> 当前 `.rgui` onclick 解析仅支持纯函数名（`onclick="fn"`），不支持参数。
> RS03 通过双向映射 + `handle_click` 传入 widget_id → Rhai 函数可就近获取上下文，
> 无需参数。未来可扩展 onclick 参数语法，但不阻塞 MVP。

#### 第 2 层：StateStore 集成（RS05-RS06）

利用 D2 已有的 `StateStore` + `StoreAccessMut` + Subscription 机制，
让 Rhai 直接读写持久状态，变更后仅重建受影响 widget。

- **RS05 Rhai↔StateStore 绑定** — 注册 `store_read(id)` / `store_write(id, value)`
  函数，Rhai 直接访问 D2 持久状态层。
- **RS06 Subscription 驱动的增量重绘** — Widget 通过
  `StoreAccess::subscribe(id)` 监听状态变更→dirty 标记→仅重绘受影响 widget
  （利用已有 diff/patch 机制）。

#### 第 3 层：完整响应式（RS07）

- **RS07 `.rgui` 声明式数据绑定** — 支持 `expanded="{state.s1_open}"` 语法，
  自动建立订阅关系，无需手写 set_prop。

> **Animated\<T\> 接线**（原独立任务，现合并到 RS07）——声明式绑定自动触发 Animated 过渡。

## 11. 边界情况处理

| 情况 | 处理 |
|------|------|
| 热重载期间用户操作 | 事件排队，热重载完成后批量处理 |
| 快照序列化失败 | 记录错误，跳过本次快照，下次重试 |
| AppProcess 版本不兼容 | framework_version 比对，不匹配时全量重建 |
| 连续保存（debounce） | 合并 300ms 内多次保存为一次重载 |
| 快照 > 100MB | zstd 压缩 + 分块传输；延迟恢复超大状态 |
| DisplayProcess 崩溃 | AppProcess 退出；用户重新启动 |
